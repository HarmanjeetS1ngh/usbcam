# UsbCam handoff (update at the end of every milestone)

## Goal
DroidCam-style Android app: phone camera -> PC over USB, lowest latency, native resolution
(up to 4K60 where the phone's hardware encoder allows), controllable from PC, appears in OBS 33.0.3.
Test phones: Samsung Galaxy S22, Realme 7 (old, likely no 4K60 HW encode). Must be light on phone and PC.
PC: Windows, Ryzen 5 5600H, RX 5500M, VS Code only (no Visual Studio). Builds via GitHub Actions.

## Decisions (do not re-debate)
- Transport: ADB over USB. Phone app listens on 127.0.0.1:5000; PC uses `adb forward tcp:5000 tcp:5000`.
- Phone: Kotlin, no dependencies, Camera2 -> MediaCodec hardware H.264, Surface input, no preview.
- Stream: raw Annex-B H.264 over TCP (SPS/PPS prepended to every IDR). Small queue, drop + resync on keyframe.
- PC (M3): hardware decode via D3D11VA (AMD VCN). OBS (M4): native OBS source plugin first
  (build from obs-plugintemplate on GitHub Actions); virtual camera driver later, if wanted.
- Modes are never hardcoded: query MediaCodecList / Camera2 per device, offer only what is supported.
- "Zero latency" is not literal; target < 80 ms glass-to-glass.

  - Control channel (port 5002, `adb forward tcp:5002 tcp:5002`, loopback only): newline-delimited JSON, one reply line per request, one client.   - Buffer pool: 10 reusable buffers (256 KB start, grow on demand) with the 13 header bytes reserved in front, so one write per frame and no per-frame allocation. Queue still 6; pool exhausted or queue full => drop all + wait for next keyframe.

## M11 Windows virtual camera "UsbCam Camera" (PC side only; phone app untouched, NOT COMPILED, NOT RUN)
- Route chosen: (a) Media Foundation virtual camera (MFCreateVirtualCamera, Windows 11 build >= 22000) with our own custom media source DLL. The user's `winver` was not known when this was written: if it is Windows 10, a DirectShow fallback (b) is a separate job. Licensing: all code original, no OBS/GPL code, no third-party code.
- New files: `pc-vcam/vcam_shared.h` (shared-memory layout), `pc-vcam/usbcam_vcam_src.cpp` + `.def` (camera DLL, static CRT, loaded by Windows' Frame Server), `pc-vcam/usbcam_vcam.cpp` (feeder exe), `pc-vcam/CMakeLists.txt`, `.github/workflows/build-vcam.yml` (artifact `usbcam-vcam`: exe, dll, FFmpeg DLLs, install scripts), `pc/build-vcam.ps1`, `pc/vcam-install.ps1`, `pc/vcam-uninstall.ps1`. - Architecture: `usbcam_vcam.exe` (user session, console exe, started hidden by the tray) creates the virtual camera (Session lifetime, CurrentUser => camera exists while the exe runs, disappears when it exits or the tray says Off) and listens on 127.0.0.1:5003 (JSON lines: `status`, `mirror {on}`, `quit`). The DLL is registered once in HKLM (regsvr32) at `C:\Program Files\UsbCam\vcam` (LocalService must be able to read it). Frame Server loads the DLL; the DLL creates the shared memory `Global\UsbCamVcamFrames` + event `Global\UsbCamVcamFrameEvent` (fallback `Local\...`) with an Everyone + Low-integrity security descriptor (a normal user cannot create Global objects, so the DLL creates and the feeder opens; the feeder polls every 0.5 s).
- Frame path: phone H.264 -> viewer's code (adb forward, control `start {hdr:true}`, D3D11VA decode, newest wins) -> crop-to-fill (centre) + scale + optional mirror to the size the apps asked for (1280x720 or 1920x1080, own bilinear code, plain memcpy when the phone size already matches) -> 4 NV12 slots round robin in shared memory (no queue; reader checks the writer did not lap the slot) -> DLL converts only the format the app selected (NV12 copy, YUY2, RGB32; BT.709 limited) and answers Frame Server's RequestSample with the newest frame; no new frame within 66 ms => repeats the last one (so apps always get frames). Types offered: NV12, YUY2, RGB32 x 1280x720 / 1920x1080 at 30 fps; MF_DEVICESTREAM_FRAMESERVER_SHARED=1 (Frame Server shares one stream between all apps = the multi-app mechanism).
- "Waiting for phone": the feeder draws it (GDI; dark picture, phone outline, animated dots, one line of reason: unplug / app not running / camera switched off in the app / connection lost) whenever no live frame arrived for 0.8 s. It is written only when its content changes. If the feeder is not running the camera does not exist (no dead camera). Recovery is automatic (net loop retries; viewer logic).
- Idle behaviour (saves phone battery/heat): the DLL writes a heartbeat while an app has the camera started. No app for 15 s (`--idle n`) => feeder sends `stop` to the phone and closes the video socket (this also frees port 5000 for the viewer/OBS: the phone accepts ONE video client at a time, so viewer/OBS and the virtual camera cannot stream at the same time; the tray's "Open viewer window" only works while no app uses the virtual camera). Starting an app takes ~1-3 s to get the first phone frame (placeholder shown meanwhile).
- Log: `%TEMP%\usbcam-vcam.log` (feeder; install log: `%TEMP%\usbcam-vcam-install.log`). Every 5 s while an app uses the camera one `[stats]` line: phone fps, decode ms, crop/scale/write ms, `cam->vcam` ms (camera timestamp -> frame written for the apps, same clock logic as the viewer), `vcam->FrameServer` avg/max ms (written -> handed to Frame Server, measured in the DLL, passed back through shared memory), fps to apps + repeats, CPU % of the feeder and of the Frame Server process (if readable), GPU % of the busiest engine of the feeder (PDH "GPU Engine", every 10 s). The latency added by us = crop/scale/write + vcam->FrameServer (target <= 30 ms); Frame Server -> app is not measurable from here (use the stopwatch method).
